Minecraft Launcher & 24/7 Paper Server Guide

Last updated: November 2026

Hit Play to launch Minecraft. Below, you will find the full guide to running your own 24/7 Paper server — practical configuration guidance, realistic RAM sizing, and the JVM settings that help keep tick time stable on a VPS.

Why Paper instead of Vanilla or Realms for a 24/7 server

Vanilla is the reference implementation for a Java Edition server, and it is a sensible starting point for a small private world. As the world grows, however, the server has more chunks to load, entities to tick, block updates to process, and player actions to handle. Paper is a server implementation built on the Minecraft server code with performance work, configuration options, and a plugin API. It can reduce avoidable server work and gives an administrator more control over gameplay systems that affect tick time. Paper does not make a slow CPU fast, and it cannot eliminate the cost of a huge view distance or an overloaded world, but it gives you practical tools to tune a long-running server without changing the client.

Realms is convenient when the priority is a managed, low-maintenance world for a small group. You do not administer the underlying machine, install arbitrary server plugins, choose the Java heap, or tune the same range of server settings available on a self-managed Paper host. A dedicated Paper server is a better fit when you want plugins, scheduled maintenance, custom permissions, a controlled backup process, or room to change hardware as the community grows. The trade-off is responsibility: you must secure the operating system, keep the server updated, monitor resource use, and test backups. Choose Paper because you need that control, not because the word “optimized” guarantees a particular number of players.

Realistic RAM, CPU, storage and bandwidth sizing

Use the table as a starting point for a newly provisioned server, not as a guarantee. Actual memory use depends on the Minecraft version, world size, loaded chunks, plugins or mods, entity counts, player travel, and the number of players active at the same time. The minimum column is a constrained starting point; the recommended column leaves more room for the Java heap and normal workload variation.

Server TypePlayersMin RAMRec. RAMStorage
Vanilla2–52 GB3 GBNVMe
Paper + Plugins10–204 GB6 GBNVMe
Modded5–106 GB8 GBNVMe
Large Modpacks5–158 GB12 GBNVMe

For a typical Paper server, pay close attention to single-core CPU performance. The main game tick has work that must be completed in sequence, so a high clock speed and strong per-core performance can matter more than a large advertised core count. Extra cores are still useful for the operating system, networking, plugins that perform asynchronous work, backups, and other services, but eight slow shared vCPUs do not automatically outperform a smaller allocation with faster, consistently available CPU time. Ask a provider whether its plan uses shared, burstable, or dedicated vCPUs, and treat “dedicated” as a plan feature to verify rather than a label to assume.

Choose NVMe SSD storage for the world, region files, and server files whenever the budget allows. Chunk generation and loading involve many reads and writes; a busy HDD can add latency when players explore new terrain or when the server saves region data. SATA SSD storage is generally preferable to a mechanical disk, while NVMe offers higher throughput and strong random-I/O performance on suitable hardware. Storage speed is not a substitute for CPU or RAM, but a fast drive helps avoid storage becoming the weak link. For bandwidth planning, a rough working allowance is 50–150 KB/s per active player in each direction under ordinary play; plugins, voice chat, map rendering, frequent chunk movement, and backups can change that figure. Check the host's transfer allowance and network limits rather than assuming an unlimited port means unlimited monthly traffic.

VPS vs dedicated game hosting vs home hosting

Shared game hosting is usually the simplest way to start. The provider supplies a control panel, a server template, and routine infrastructure management; you select a plan and upload or configure the world. That convenience can be worth the price when you do not want to administer Linux. The limitation is that the provider controls the underlying environment. CPU time may be shared with other customers, available Java options may be restricted, and unusual plugins or custom services may not fit the panel. Compare the actual CPU allocation, RAM limit, storage type, backup policy, DDoS mitigation, and rules for moving your world before choosing a plan. A low monthly price is not useful if the server regularly competes for CPU time during busy periods.

A home server gives you physical control and can reuse hardware you already own, but it also makes you responsible for power, cooling, router configuration, operating-system updates, and a stable internet connection. Residential upload capacity, changing public IP addresses, carrier-grade NAT, and the lack of upstream DDoS protection can make public hosting difficult. A bare-metal dedicated server provides the most direct hardware control and can make sense for a large, consistently busy community, but it usually costs more and requires more administration. For a growing community that needs root access without managing a physical machine, a KVM VPS with a clearly specified dedicated-vCPU allocation, adequate RAM, NVMe storage, and network-level DDoS protection is often the practical middle ground. It gives you control over Java, Paper, firewall rules, backups, and plugins while leaving the physical host and network infrastructure to the provider.

Step-by-step Paper install on Ubuntu

These steps assume a fresh Ubuntu 22.04 or 24.04 VPS, SSH access through an account with sudo privileges, a public IP or DNS name, and enough free disk space for the server JAR, world files, logs, and backups. Paper 1.21 requires Java 21, so install a Java 21 runtime first. Keep Ubuntu updated, use a firewall, and do not run the Minecraft process as root. The commands use a dedicated Linux account named minecraft; run package and service administration commands from your normal sudo-enabled account.

sudo apt update
sudo apt install openjdk-21-jre-headless

Create a separate account so the Minecraft process does not inherit your personal account's permissions. Create its server directory, switch into the account, and download the Paper JAR. This URL is the specific Paper 1.21 build supplied for this example; before deploying a new world, check Paper's official downloads for a current supported build and update the filename accordingly. Keep a copy of the previous JAR and back up the world before replacing a production server version.

sudo adduser --system --home /opt/minecraft --group minecraft
sudo install -d -o minecraft -g minecraft /opt/minecraft/server
sudo -u minecraft -H bash
cd /opt/minecraft/server
wget https://api.papermc.io/v2/projects/paper/versions/1.21/builds/130/downloads/paper-1.21-130.jar -O paper.jar

Start the server only after reviewing the Minecraft End User License Agreement. The server requires explicit acceptance before it will run. Set eula=true only if you have read and agree to the EULA; do not treat this file as a way to bypass its terms. Keep the server files owned by the dedicated account and avoid granting the Minecraft process write access to unrelated directories.

cd /opt/minecraft/server
printf 'eula=true\n' > eula.txt

Create a start script to keep the Java command and heap settings in one place. This first-run example uses a 4 GB heap; adjust the values to the VPS size and memory guidance below. The script changes into the server directory before launching Paper so that world data and configuration files are created in the intended location.

cat > /opt/minecraft/server/start.sh <<'EOF'
#!/usr/bin/env bash
set -e
cd /opt/minecraft/server
exec java -Xms4G -Xmx4G -jar paper.jar nogui
EOF
chmod 750 /opt/minecraft/server/start.sh
exit

Set ownership and create a systemd service so the server can start at boot, restart after an unexpected exit, and write logs to the system journal. The service runs as minecraft, uses the server directory as its working directory, and allows time for a graceful shutdown. After saving the unit, reload systemd, enable the service, and inspect its status and logs.

sudo chown -R minecraft:minecraft /opt/minecraft
sudo chmod 750 /opt/minecraft/server/start.sh
sudo tee /etc/systemd/system/minecraft.service > /dev/null <<'EOF'
[Unit]
Description=Minecraft Paper Server
Wants=network-online.target
After=network-online.target

[Service]
User=minecraft
Group=minecraft
WorkingDirectory=/opt/minecraft/server
ExecStart=/opt/minecraft/server/start.sh
Restart=on-failure
RestartSec=10
TimeoutStopSec=120
KillSignal=SIGINT

[Install]
WantedBy=multi-user.target
EOF
sudo systemctl daemon-reload
sudo systemctl enable --now minecraft
sudo systemctl status minecraft --no-pager
sudo journalctl -u minecraft -n 80 --no-pager

Allow the default Java Edition server port, TCP 25565, through both the Ubuntu firewall and any firewall in the VPS provider's control panel. Standard Java Edition connections use TCP; do not open UDP 25565 unless you have installed an additional service that specifically requires it, such as a compatible Bedrock bridge. Allow SSH before enabling UFW so you do not lock yourself out. For a public server, use provider-level DDoS mitigation, SSH keys, and restrictive firewall rules; do not expose database or panel ports that players do not need.

sudo ufw allow OpenSSH
sudo ufw allow 25565/tcp
sudo ufw enable
sudo ufw status verbose

Test a connection before sharing the address. If the service fails, inspect journalctl -u minecraft, confirm Java 21 is installed, check file ownership, and verify the JAR filename. If local connections work but external players cannot join, check the provider firewall and public address; JVM flags will not fix a blocked port. Keep a known-good JAR and a tested backup before upgrading Paper or installing plugins.

Aikar's JVM flags

The JVM's default garbage-collection settings are designed for a broad range of Java applications, not specifically for a Minecraft server that must complete game ticks predictably. Poor heap sizing and large collection cycles can cause pauses that players experience as delayed block updates, rubber-banding, or short periods of unresponsiveness. A tuned G1GC profile can make memory collection more predictable for a suitable heap, but flags cannot compensate for a saturated CPU, an overloaded plugin, excessive entities, or slow storage. Treat this as a starting profile for Paper on Java 21 and test it against your actual workload; it does not guarantee a fixed TPS.

java -Xms6G -Xmx6G -XX:+UseG1GC -XX:+ParallelRefProcEnabled -XX:MaxGCPauseMillis=200 -XX:+UnlockExperimentalVMOptions -XX:+DisableExplicitGC -XX:+AlwaysPreTouch -XX:G1NewSizePercent=30 -XX:G1MaxNewSizePercent=40 -XX:G1HeapRegionSize=8M -XX:G1ReservePercent=20 -XX:G1HeapWastePercent=5 -XX:G1MixedGCCountTarget=4 -XX:InitiatingHeapOccupancyPercent=15 -XX:G1MixedGCLiveThresholdPercent=90 -XX:G1RSetUpdatingPauseTimePercent=5 -XX:SurvivorRatio=32 -XX:+PerfDisableSharedMem -XX:MaxTenuringThreshold=1 -Dusing.aikars.flags=https://mcflags.emc.gs -Daikars.new.flags=true -jar paper.jar nogui

First, do not allocate all VPS memory to -Xmx. The Java heap is only one part of the process. Linux also needs memory for the kernel and filesystem cache, while the JVM uses native allocations and thread stacks; monitoring, networking, and backup tools need room too. On an 8 GB VPS, a 6–6.5 GB heap can be a reasonable starting point for some Paper workloads, leaving roughly 1.5–2 GB for the operating system and non-heap use. On a 4 GB VPS, do not copy the 6G example: start with a smaller heap, perhaps around 2.5–3 GB, and monitor memory pressure. If the machine swaps heavily or the kernel kills Java for running out of memory, reduce the heap or move to a larger plan.

Second, keep -Xms equal to -Xmx for this fixed-heap setup. Matching the initial and maximum heap gives the JVM a consistent heap size instead of repeatedly expanding it as workload changes. That is why the sample uses -Xms6G -Xmx6G. Equal values do not mean the heap should consume the whole machine: both values must fit comfortably inside physical RAM. Change them together when resizing, restart during a maintenance window, and compare memory use, garbage-collection behavior, and tick health after the change.

Optimization checklist for 24/7 uptime

  • Pre-generate with Chunky. Exploring new terrain can trigger chunk generation while players expect normal gameplay. Use the Chunky plugin to pre-generate a defined world border before opening the server, then expand it deliberately as the community needs more space. Schedule heavy generation outside peak hours and watch CPU, disk I/O, and free storage while it runs. Pre-generation moves much of that work out of live play; it does not remove the need to monitor the server.
  • Start with view-distance 6–8 and tune simulation distance separately. In server.properties, a view distance of 6–8 chunks is a practical starting range for many small-to-medium Paper worlds. Simulation distance controls how far away entities and other world mechanics are processed; start around 4–6 and raise it only when the CPU has headroom. Higher values increase world-data and simulation work, so do not max both settings by default. Change one setting at a time and compare tick health with a similar player count.
  • Schedule maintenance without interrupting saves. Use a planned window for Paper and plugin updates. A cron entry that kills Java is unsafe because it can interrupt world saves. Prefer a systemd timer or maintenance script that sends a graceful stop through the server console, waits for shutdown to finish, verifies the service has stopped, and starts it again. If you administer the server in tmux, keep the session persistent and use the console's stop command rather than terminating the process abruptly. Back up before updates and retain logs for troubleshooting.
  • Configure Paper anti-xray and entity limits deliberately. Review Paper's anti-xray settings if players can expose valuable ores by inspecting terrain, and choose an engine mode and hidden-block list that fit your world. Set reasonable entity activation ranges, mob caps, and despawn behavior so farms do not accumulate thousands of active entities. Do not copy aggressive limits blindly: test villager trading, redstone, farms, and plugins so performance tuning does not break expected mechanics. Document each change so it can be rolled back.
  • Monitor /tps and investigate slow ticks. Check recent and longer-term averages instead of reacting to a brief dip during startup or world generation. A healthy server aims to sustain 20 ticks per second; when the average falls below 20, inspect timings or a profiler, CPU saturation, entity counts, plugin activity, garbage collection, and disk latency. TPS is an outcome, not a diagnosis. Record the time of a lag report, player count, recent changes, and relevant logs so recurring causes can be identified. Add an external uptime check that tests whether the server port responds, because a running process can still be unreachable.

Uptime is a routine, not a single setting. Patch Ubuntu and Java, test Paper and plugin updates in a staging copy, monitor free disk space, and store backups somewhere other than the VPS holding the live world. Test a restore periodically; a backup that has never been restored is only an assumption. Keep an incident checklist with the provider console, backup location, service commands, and last known-good JAR so recovery is methodical rather than improvised.

Monthly cost breakdown

For a small, lightly modded Paper server, a realistic starting budget is often about $5-$15 per month for a budget VPS, with backups or extra storage potentially adding to the bill. A managed shared host may cost around $10-$25 and can be worth the difference if you value a control panel and support. A stronger VPS commonly lands around $20-$40; dedicated hardware starts higher and may also bring setup fees, taxes, backup charges, or bandwidth costs. Budget separately for off-site backups and a domain if you want one, and check introductory versus renewal pricing before paying annually.

Common mistakes

  • Allocating all RAM to -Xmx: Linux, Java’s non-heap memory, and other services also need memory. Leave a sensible reserve instead of assigning the entire VPS to the Minecraft heap.
  • Using HDD storage: World loading, chunk generation, and saves can involve many small reads and writes. Prefer SSD or NVMe storage for a smoother server experience.
  • Running modpacks on 2 GB: Large modpacks and their startup process generally need more memory. Check the pack’s requirements and allow extra headroom rather than expecting a 2 GB plan to handle it.
  • No backups: Hardware failure, accidental commands, corruption, or a bad update can destroy a world. Keep scheduled backups off the server and periodically test restoring one.
  • Opening the world before pre-generation: Unexplored terrain can trigger expensive chunk generation while players are online. Pre-generate the expected play area with a tool such as Chunky, then expand it in controlled stages.

Frequently Asked Questions

How much RAM do I need for 20 players?
For a typical Paper server with plugins, 4-6 GB of heap is a reasonable starting estimate for around 20 players. Actual needs depend on plugin load, view distance, world activity, and how much exploration happens at once, so monitor memory and tick performance after launch.

Can I run a Paper server on a 4 GB VPS?
Yes. A 4 GB VPS can be suitable for a small server of roughly 10-15 players with a modest plugin set and carefully tuned settings. Do not give all 4 GB to -Xmx; the operating system and Java need memory too, and a busy world may require a larger plan.

Do I need a dedicated IP?
No. A dedicated IP is optional. It can make DNS setup and sharing a server address more straightforward, but a domain name can also point to a server address, and a non-default port may need to be included when connecting.

Is a VPS better than Realms?
A VPS is generally more flexible if you want Paper plugins, control over Java and server settings, custom backups, and the ability to manage capacity yourself. Realms is simpler to operate because hosting is managed for you. The better choice depends on whether you value customization and administration or convenience.

How much CPU does a Minecraft server need?
Prioritize strong single-core performance over a high advertised core count. Minecraft’s main server tick work is sensitive to the speed of one core, although additional cores can help with other tasks and services. Look for a recent CPU with good sustained performance, not just a large number of vCPUs.
